# Agent Hub 逐页演讲稿

建议按约 25 分钟准备，实际时长以排练为准。重点放在第 3–8 页的角色与 Workflow；格式页可简讲。

本稿根据当前项目文件组织。示例提示词和补漏对比不代表历史对话；真实截图与实际运行结果尚待补充。

使用：打开 index.html，用方向键翻页。按 N 显示或隐藏讲述提示，提示会出现在投影页面中，正式分享前应关闭。按 F 进入全屏。

## 第 1 页｜开场

**讲图提示：**今天沿着需求、角色、流程、文件和迭代，分享如何与 AI 一起把想法做具体。

大家好，今天想结合 Agent Hub，分享我们怎样和 AI 一起把一个想法逐渐做成有明确结构的项目。我会重点讲其中的设计和沟通过程：需求怎样拆成角色，角色怎样形成工作流，以及这些讨论怎样落实到文件里。

这次展示的主要是项目设计和定义。涉及运行效果的部分，需要以实际调用和结果为依据。

## 第 2 页｜从想法到实现：这次分享沿着什么顺序展开？

**讲图提示：**先解释想解决什么，再说明如何设计协作，最后落实到文件并检查。

Agent Hub 的起点，是希望用户描述一个业务目标后，就能找到合适的 Agent，并在需要时组织多个能力一起完成任务。

接下来按这四步展开：先明确用户需要什么，再设计角色和流程，然后把约定写成 AI 能读取的文件，最后通过提问和检查不断调整。这样的顺序，也方便我们知道每一次和 AI 对话究竟在解决哪一层问题。

## 第 3 页｜先拆需求，再确定主 Agent、功能 Agent 和业务 Agent

**讲图提示：**指左侧用户问法，再指右侧三层角色；角色来自工作需要。

确定角色时，可以先把需求里的工作列出来。比如，用户需要一个统一入口来理解目标、解释方案、取得确认，这些工作交给 Hub。

当用户不知道找谁、任务需要多个步骤、执行中需要跟踪状态，或者现有能力不足时，就分别对应 Finder、Builder、Executor 和 Creator。至于版本比较、影响分析、简报草拟，则属于具体的业务能力。

这里值得分享的是：先根据工作拆职责，再确定 Agent。和 AI 讨论时，可以让它列出每个角色的输入、输出和边界，看看有没有重复或遗漏。

## 第 4 页｜职责怎样划分：Hub 管整体，功能 Agent 各自交付

**讲图提示：**从用户向下讲 Hub、功能 Agent、业务 Agent；强调每层交付与边界。

这张图把分工关系串起来。最上面是用户，Hub 是统一的交互入口，负责理解、路由、确认和汇总。

框内的功能 Agent 各自返回交付物：Finder 返回候选与理由，Builder 返回工作流蓝图，Creator 返回缺口分析和方案，Executor 返回执行状态与结果。业务 Agent 则处理具体任务，由 Executor 按授权组织调用。

图中展示的是协作关系，一次请求不一定经过所有角色。设计时需要追问的是：每一步结束以后，交给谁，交付什么？

## 第 5 页｜Workflow：先画主线，再补关键判断

**讲图提示：**沿主线向下指，停在蓝框：理解、匹配和编排是重点。

有了角色，下一步就是画工作流。这里先看主线：用户提出需求，Hub 理解和判断，寻找能力，必要时编排，确认后执行，最后审核结果。

蓝框是我们重点讨论的区域。因为用户不会总按同一种方式提问，所以同一条主线里还需要明确判断条件。接下来只取三个片段，看看这些条件怎样变成具体规则。

## 第 6 页｜片段 1：先判断用户到底想做什么

**讲图提示：**对比“有哪些 Agent”和“帮我处理”，说明两种意图的不同路径。

第一段先判断用户的意图。“有哪些 Agent”和“帮我处理这两份文件”，表面上都在和 Hub 对话，但期待的结果不同。

前者需要概览或推荐，后者需要检查任务和输入，准备执行路径。如果目标不清楚，先问必要的问题；如果目标清楚、只是材料还没有给，可以先讨论适合的能力，执行要等待材料。

和 AI 沟通时，我们需要把这种区别写出来，让每个分支都有明确的下一步和停止条件。

## 第 7 页｜片段 2：决定怎么找到合适的 Agent

**讲图提示：**先讲已指定，再讲未指定；核验与推荐最后汇合到明确候选和范围。

第二段是怎样选择 Agent。用户没指定对象时，交给 Finder；用户已经指定时，先检查这个 Agent 是否存在、适合当前任务，以及实际是否可以运行。

指定有效，可以省去重新推荐；指定不适合，就需要解释原因，再推荐替代。这里还要区分目录里的 Active 和实际可运行状态，定义完成不等于已经连接好工具。

这段流程适合用来说明，用户的一句话往往包含多个需要设计者判断的条件。

## 第 8 页｜片段 3：把复杂任务拆成可以交接的步骤

**讲图提示：**指 Builder 蓝框：比较结果交给影响分析，再一起交给简报草拟。

第三段是复杂任务。比如比较两版 SOP、分析影响、再形成简报，这里面有明确的步骤依赖。

看蓝框里的 Builder，它要把每一步接收什么、交付什么写清楚。比较步骤输出带来源的差异清单，影响分析接收这些差异和已知流程依赖，简报步骤再接收前面的结果、受众和篇幅要求。

所以让 AI 编排时，不能只要求列出几个 Agent 名称，还要要求它写清输入、输出、依赖和权限范围。

## 第 9 页｜把前面的设计写进 README，让 AI 有据可依

**讲图提示：**设计清楚之后，用 README 保存共同约定；每轮明确让 AI 先读。

前面的设计讨论清楚以后，怎样让之后的 AI 对话继续沿用这些约定？项目里用 README 集中保存背景和规则。

这里放项目愿景、角色架构、交互与路由规则，以及文件和定义标准。后续提出修改时，可以先明确要求 AI 阅读相关部分，再说明本次要改什么。

README 提供持续可引用的上下文；在新的任务里，仍要说明应该读取哪些文件，以及当前的具体目标。

## 第 10 页｜README 也记录“为什么这样做”和“还有什么没定”

**讲图提示：**左侧是接受的决策，右侧是未定事项；避免把猜测变成要求。

README 里还有两块很有用：Decision Log 和 Open Questions。

已经接受的决策，需要留下内容和理由，比如为什么由 Hub 统一交互、为什么初期用 TXT 保存定义。暂时未定的事情，则单独记录，避免 AI 把一个讨论中的选项写成既定方案。

这也方便我们自己复盘：当一个要求发生变化时，先修改明确的决策，再同步受影响的定义和索引。

## 第 11 页｜告诉 AI：每类内容具体存在哪里

**讲图提示：**按目标与规则、指令与能力、待办与验证三组介绍文件。

这一页可以按三组看。第一组是目标与约定，主要在 README；第二组是具体定义，包含主 Agent、功能 Agent 和业务 Agent；第三组是发现与维护，包含 Registry、TODO 和测试材料。

这样安排以后，和 AI 沟通可以具体到文件。例如，修改入口判断就检查 Agent-Hub.txt，调整业务能力就修改对应 TXT，新增能力以后还要同步 Registry。

文件位置清楚，后续任务的修改范围也更容易说明。

## 第 12 页｜“我的格式放在哪里？”——先给 AI 一份可引用的规范

**讲图提示：**区分四个规范位置：通用规范、业务细则、内部返回、用户展示。

格式并不是只放在一个模板里。根 README 规定通用标准，业务目录 README 补充业务 Agent 细则，各个 TXT 的 Return format 规定内部交接字段，而用户展示方式由单独的输出规则约定。

这几层解决的问题不同：文件怎么写、业务定义补什么、Agent 之间怎么传结果，以及 Hub 怎样向用户解释。要求 AI 生成内容时，可以明确让它依次参考这些约定。

## 第 13 页｜一个 Agent 文件，最外层固定三部分

**讲图提示：**沿 Name、Description、Instruction 三段讲；这是本项目约定。

落到一个 Agent 文件，最外层固定三部分：名称、Description 和 Instruction。

Description 负责快速说明能力、使用时机和必要限制；Instruction 才展开具体行为。本项目还约定 Description 的字符数和整个文件的长度，并为业务 Agent 保留中英文名称。

这类格式要求适合写成可检查条件。提出“统一格式”以后，还需要明确统一到哪几个字段、什么长度，以及哪些限制不能在精简时被删掉。

## 第 14 页｜Instruction：从“你是谁”写到“你该怎么做”

**讲图提示：**用“缺了两版文本怎么办”说明输入、边界和状态必须具体。

Instruction 要进一步回答：什么时候调用，需要什么输入，按哪些规则处理，缺材料怎么办，最后返回什么。

比如版本比较 Agent，需要两版可读文本。如果任务要求判断新旧变化，还需要明确版本顺序。缺少这些信息时，应返回澄清需求，不能凭文件名猜测。

把这些条件写清以后，AI 生成的定义才更接近可执行的规则，也更容易检查边界。

## 第 15 页｜真实例子：让差异比较结果能交给下一个 Agent

**讲图提示：**挑 status、missing_fields、observed_change 与 possible_implication 四个字段讲。

这一页不需要逐行读字段，可以重点看四处。status 表明完成、需要澄清还是失败；missing_fields 说明缺什么；observed_change 保存观察到的变化；possible_implication 保存可能的影响。

把观察和影响分开，后面的 Agent 就能知道哪些是来源直接支持的内容，哪些还需要验证。版本和覆盖范围同样要传下去，避免局部比较在后续被说成全文结论。

## 第 16 页｜文件写好了，还要让其他 Agent 找得到它

**讲图提示：**TXT 说明能力怎么做，Registry 说明能力怎么被发现，修改时需同步。

写好 TXT 以后，还需要让 Finder 找得到它。TXT 描述这项能力怎样工作，Registry 则保存发现和比较能力所需的元数据。

新增或修改 Agent 时，要同步名称、描述、分类、标签、权限和状态，检查两边有没有冲突。否则可能出现定义已经变了，但推荐仍根据旧信息进行的情况。

所以我们给 AI 的任务也应包括同步和检查，而不是只生成单个文件。

## 第 17 页｜流程怎么补漏：用一个追问发现缺失的分支

**讲图提示：**这是补漏讲解示例，非历史第一版；用指定 Agent 的追问补充分支。

这一页用一个构造的补漏示例说明迭代方法，不代表项目历史第一版就是上面的简化流程。

如果流程只写“收到需求后推荐 Agent”，我们可以追问：用户已经指定了 Agent 怎么办？这个 Agent 不合适又怎么办？追问之后，就能补出先核验、有效时确认执行、无效时推荐替代的分支。

有真实对话后，可以用实际反馈和修改记录替换这里的示例，讲清当时发现了什么，以及规则怎样变化。

## 第 18 页｜怎么检查流程：用用户提问走一遍规则

**讲图提示：**选两条问题推演，指出命中的规则、下一步与停止条件。

检查流程时，可以拿几句用户提问走一遍。不一定要一下覆盖所有情况，先选能触发不同判断的代表问题。

比如目录查询，应该停在概览；多步骤任务，应该有输入输出交接；第二步失败，应该能说明已经完成什么、接下来怎么处理。

请 AI 推演时，可以要求它列出每一步命中的规则、下一步和停止条件。这里检查的是规则是否自洽，实际调用有没有发生，还需要运行记录验证。

## 第 19 页｜修改需求时，告诉 AI 同步改哪些地方

**讲图提示：**按规范、定义、Registry、检查顺序说明一次修改影响哪些文件。

发现问题以后，一次修改通常会影响多个文件。比如 Description 的写法变化，要先明确新规范，再修改具体定义，同步 Registry，最后检查长度、字段和引用。

给 AI 反馈时，可以把这个范围直接说明：哪些规范需要改、哪些定义受影响、哪些索引要同步。完成后要求它列出实际修改和未完成项，方便我们审阅。

## 第 20 页｜把笼统的修改要求变成可以验收的任务

**讲图提示：**把“优化一下”改成可检查的长度、字段、边界和一致性要求。

很多修改效果不好，是因为要求还不够具体。比如“精简一点”，可以改成“一段英文，保留能力、触发条件和重要限制，并控制在规定字符数以内”。

“检查重复”也可以具体成比较输入、输出、触发条件和边界，再给出重叠证据。这样 AI 提出的建议更容易审核，我们也知道根据什么接受或拒绝。

## 第 21 页｜最后一步：把待验证事项写下来，交给下一轮

**讲图提示：**待办追踪进度，测试材料约定验收；文本推演与运行证据分别记录。

还有一部分工作暂时不能当场完成，需要进入 TODO 和测试材料。

TODO 保存进度、待办和完成标准；测试材料则准备输入、操作步骤、预期和通过条件。定义整理完成、工具配置完成、运行验证通过，应该分别记录。

这样下一次和 AI 继续工作时，就有明确起点，也能避免把“规则写好了”误当成“系统已经验证通过”。

## 第 22 页｜我们和 AI 怎样分工：决定、展开、审核与沉淀

**讲图提示：**指左侧人的判断、右侧 AI 的展开，再沿循环说明反馈如何写回文件。

回头看整个过程，人的工作主要是确定目标、做关键决策并审核业务含义；AI 可以帮助展开情况、提出分支、整理指令和同步文件。

这个分工会形成循环：提出目标，得到方案，审核并指出偏差，再把接受的结果写回项目文件。我们需要持续参与的，就是判断方案是否符合原来的意图，以及实际结果是否支持结论。

## 第 23 页｜用一段真实对话串起：需求、设计、修改与结果

**讲图提示：**素材待补：拿一次真实需求、AI 回应和文件修改，展示完整协作过程。

这一页准备放真实材料，目前先保留位置。分享时可以只选一次具体修改：先展示提出的要求，再展示 AI 的回应，最后看文件究竟改了哪里。

重点讲自己做出了什么判断、为什么继续追问，以及最后的规则是否更清楚。没有历史素材时，可以跳过这一页，或明确按示例说明，避免把整理后的提示词说成原始对话。

## 第 24 页｜结尾

**讲图提示：**回扣背景、规范、实现与检查；真实案例与规则共同构成项目上下文。

今天想分享的方法是：先把业务需求拆成角色和流程，再用文件保存背景、规范与决策，让 AI 据此实现，并通过具体问题检查和迭代。

对我来说，有用的沟通往往包含三件事：清楚的上下文、具体的要求，以及可以核对的结果。希望这次 Agent Hub 的例子，能给大家组织自己的 AI 协作项目提供一些参考。
