## 第 1 页｜开场

对应页面：Building Agent Hub with AI

**讲图提示：**先介绍今天分享的是实现与沟通过程。

大家好，今天想结合 Agent Hub，分享我们怎么和 AI 一起，把一个想法逐渐变成有结构、能继续迭代的项目。

## 第 2 页｜整场快照：从 Chat 到 Agent Hub

对应页面：From Chat to Agent Hub: the whole journey at a glance

**讲图提示：**沿中央箭头从左到右讲六个图标，再指出黄色、蓝色、绿色三个阶段区域。节点下方分别是这一阶段的工作和留下的产物，不需要逐项读完。

先用这张图看整场分享。最开始是 Chat，通过对话探索想法。然后把想法整理成 Structured Prompt，明确目标、背景、输入和约束。

经过讨论确认的规则，可以保存成 Reusable Instructions，比如 README 里的共同约定和各个 Agent 的指令。再用 Workflow 明确步骤、判断和交接，形成职责清楚的 Agent 设计，最后由 Agent Hub 统一入口、协调多个能力。

这不是项目真实创建顺序的还原，也不是说把 Prompt 存下来就自动变成 Agent。真正运行还需要环境、工具、状态处理和验证。当前项目能展示设计和定义如何落实，运行效果需要实际证据。

贯穿今天的设计问题是：用户知道想做什么，却不一定知道选哪个 Agent、怎样组合。接下来我们就以 Agent Hub 为例，重点看角色和流程怎样设计，以及怎样通过文件和 AI 一起把它们做具体。












## 第 3 页｜为什么要做 Agent Hub：选谁、为什么选、怎样完成

对应页面：Why Agent Hub? From too many options to coordinated work

**讲图提示：**按左、中、右三幅图讲：散落的 Agent 表示选择困难，中间是带理由的候选排序，右边经过黄色确认节点才进入执行。候选 A/B/C 是示意，不是真实评分结果。

这一页回答为什么要做 Agent Hub。先看左边：公司 Agent 越来越多，用户知道想完成什么任务，但不一定知道该用哪个。光看名称也很难判断适不适合，自己比较的成本就变高了。这是我们的设计问题假设，不是已经做完用户调研的结论。

中间画的是示意候选清单，A、B、C 和适配等级都不是实际运行结果。它表达我们希望提供的第一步帮助：用户描述目标、材料和限制后，系统推荐合适的 Agent，并解释评分依据、优势和限制。这里的匹配评分表达任务适配程度，不是运行成功率，也不是结果准确率。

右边再往前走一步：推荐以后，还希望能帮用户把工作组织起来。简单任务使用一个 Agent，复杂任务形成多 Agent Workflow。用户确认方案、输入和权限后，再执行并交付可以审核的结果。

所以我们不是只做一个 Agent 名单，而是希望串起发现、选择和授权执行。下一页再看，为了提供这样的体验，Hub、Finder、Builder 和 Executor 的职责应该怎样分。








## 第 4 页｜和 AI 一起确定主体框架

对应页面：How we shaped the main-agent framework with AI

**讲图提示：**先指左侧关系图上方的四步过程条，再按右侧气泡讲，最后回到左侧关系图。这里确定谁负责，下一页才讨论角色按什么顺序配合。

有了统一入口、推荐和协助执行的想法以后，我先让 AI 帮忙整理系统，不急着写指令。第一轮说明想实现的体验，AI 再把中间工作拆成理解需求、能力匹配、规划、执行和缺口处理。

## 第 6 页｜判断用户意图

对应页面：Fragment 1: identify what the user wants

**讲图提示：**对比图中左右两条路径。

第一段先判断用户想得到什么。“有哪些 Agent”和“帮我比较两份文件”，虽然都在和 Hub 对话，但期待的结果不同。

前者是了解能力，返回概览或推荐就可以，后者是执行任务，需要检查目标和材料。如果目标本身不清楚，就先问必要的问题，如果目标明确、只是文件还没给，可以先讨论能力，但执行要等待输入。

让 AI 写流程时，需要同时写清楚下一步是什么，以及应该在哪里停下来。

右侧对话可以这样讲：先问“用户只是查询有哪些 Agent，是不是也需要执行”，AI 建议把浏览和执行分开。再追问“目标明确，但还没提供材料怎么办”，最后把规则明确为可以讨论合适能力，但必要输入补齐前不能执行。这里是根据项目规则整理的示例对话，不是原始聊天记录。

这一页承接初步主线，从用户的不同情况出发，通过追问补齐判断分支，而不是事后只解释现成规则。



## 第 7 页｜选择与核验 Agent

对应页面：Fragment 2: find the right agent

**讲图提示：**先指左侧过程条：初步主线、用户指定 Agent、核验或替代推荐，再讲右侧追问。

第二段是怎么找到合适的 Agent。用户没有指定时，交给 Finder 推荐，用户已经指定时，先检查它是否存在、适不适合这个任务，以及实际能不能运行。

指定有效，可以跳过重新推荐，指定不合适，就说明原因，再寻找替代。这里还要区分 Active 和 runtime readiness。Active 说明定义已完成、可以被发现，不能直接证明工具连接和运行已经通过验证。

一个看起来简单的用户请求，往往包含了好几个需要提前设计的判断。

右侧可以按对话讲：先问“指定 Agent 后还要重新推荐吗”，再追问“选错了怎么办、选择是否等于授权执行”。从这两个追问，推导出核验、替代推荐和独立执行确认三个规则，再对应到左侧分支。示例是重构对话，不是历史原文。

这一页承接初步主线，从用户的不同情况出发，通过追问补齐判断分支，而不是事后只解释现成规则。



## 第 8 页｜复杂请求怎样决定功能职责

对应页面：Fragment 3: break complex work into clear handoffs

**讲图提示：**先指左侧过程条：初步主线、多 Agent 请求、明确规划与交接，再讲右侧对话。

回到 Agent Hub 的实现：如果用户的一个请求需要多个 Agent，系统应该由谁来拆步骤、谁来执行？这正是我们需要与 AI 讨论的设计问题。

这里把规划交给 Builder，让它返回每一步的输入、输出和 dependencies，执行则交给 Executor，接收已经确认的蓝图。Hub 负责向用户解释计划并确认范围。

可以给 AI 这样的要求：不要把“规划”和“执行”写成同一个模糊职责，明确两个角色通过什么字段交接、什么时候暂停。这样 Workflow 讨论就会落实到功能指令。

右侧先问“多个 Agent 怎样配合”，让 AI 提出按步骤明确负责人、输入输出和依赖。接着追问“谁规划、谁执行、怎样交接”，把 Builder、Hub 和 Executor 的边界说清楚。绿色部分是最终规则：Builder 输出蓝图，Hub 展示并确认，Executor 接收确认后的计划再执行。这个对话是重构示例。

这一页承接初步主线，从用户的不同情况出发，通过追问补齐判断分支，而不是事后只解释现成规则。

## 第 10 页｜用泳道图和 AI 核对职责与交接

对应页面：Use a swimlane diagram to clarify who does what

**讲图提示：**页面保留 Owner、Handoff、Boundary 三个问题。讲的时候沿泳道指向对应节点，用下面的例子展开。

第 9 页检查下一步走哪里，这一页换一个角度：这一步到底谁负责，做完以后交出什么。我会让 AI 把步骤放到对应角色的泳道，再说明输入、输出和下一位接手者。

先看 **Owner**。Finder 负责匹配和推荐，Builder 负责规划，Executor 负责执行已经确认的任务。这样可以检查有没有两个角色都在做同一件事，或者某一步没有人负责。

再看 **Handoff**，我会沿着图讲三次交接：

- **Finder → Hub**：交回候选 Agent 和适配理由，让 Hub 向用户解释选择。
- **Builder → Hub**：交回方案，写清楚步骤、负责人、输入、输出和依赖，供 Hub 展示和确认。
- **Hub → Executor**：交付已经确认的方案与执行范围，让 Executor 按这个范围调度，而不是重新规划。

最后看 **Boundary**。比如需要的材料还没提供，就先暂停并返回缺失字段，由 Hub 获取输入；方案被拒绝，就回到修改或澄清，不能直接进入执行。

所以我和 AI 沟通时，不只问“几个 Agent 怎么配合”，而是逐步问：谁负责、交出什么、谁接手、什么时候停。泳道图帮助我们把这些约定摆在同一张图里核对。这里展示的是典型路径，完整判断与返回分支见上一页。

## 第 11 页｜用 AI 整理零散想法，再按约定逐步生成

对应页面：Use AI twice: organize our ideas, then work from the agreed files

**讲图提示：**先指左边三个散落便签，再指中间 AI 整理图标与 Human review，接着看三份文件，最后沿右侧三个步骤向下讲。底部虚线表示审核后回到共同参照做修正。

其实整个做法可以用这一页概括。我们一开始可能只有零散想法：角色怎么分、文字写成什么风格、README 要有哪些 section，以及后面要按哪些步骤做。

第一轮和 AI 配合，是让它帮忙归类、总结，把缺失和冲突指出来。已经确认的决定和没确定的问题要分开，由我们审核，不让 AI 自己替我们补决定。

确认后，再把这些内容写成持续可用的文件和规则。比如写作风格、格式和长度写进相关规范，README 保存目标、职责、流程和决策，step-by-step 的安排保存到 Workflow 和 TODO。

第二轮再让 AI 做事时，就明确要求它先读取这些文件，按当前步骤生成或修改内容，然后报告检查和未完成项。这样每次不只是重新说一个笼统目标，而是有共同参照和步骤可以核对。

底部还要有反馈循环。如果结果不符合意图，就判断是生成没遵守规则，还是规则本身不够清楚，再修正并写回文件，继续下一步。这里说的生成文件和后续 Agent 的真实调用要分开，运行仍要看工具、权限、授权和验证证据。

## 第 16 页｜先恢复上下文，再继续工作

对应页面：Resume without losing context or redesigning agreed work

**讲图提示：**先指左侧三个问题，再沿右侧顶部四步过程条说明继续工作的顺序，接着指参考资料栏和对话，讲恢复上下文与限定修改范围。

## 第 18 页｜两种情况怎样推动一次设计修改

对应页面：A new idea: fewer repeated prompts, clearer confirmation rules

**讲图提示：**先讲左侧两种情况及希望的处理方式，再沿右侧对话说明怎样把想法交给 AI 分析。

我做到一半想到一个使用体验问题。第一种情况，用户已经给了文本并要求总结，再问要不要开始就显得重复，我希望减少这次询问。第二种情况，用户说把总结发送给团队，这增加了一个外部动作，需要明确收件人和内容，再确认具体发送。

所以左侧不是结果表，而是我给 AI 的两个需求例子。我告诉 AI，我想去掉的是重复确认，同时保留真正需要的澄清和确认。右侧让 AI 把这个差异转成判断分支，并先列出受影响文件，供我审核，而不是直接修改。

## 第 21 页｜人与 AI 的对话泳道图

对应页面：Human judgment and AI assistance at each iteration

**讲图提示：**顶部是人和机器人两个图标。从上到下沿四条箭头讲，每次直接结合动作和说明，不再分左右介绍。

第一轮是 **Define，人到 AI**：我们提出目标、职责边界和要求，先把方向说清楚。

第二轮是 **Develop，AI 到人**：AI 整理想法、提出方案，生成供我们检查的文件。

第三轮是 **Review，人到 AI**：我们检查业务含义、冲突和依据，给出具体修改意见，而不是只说再优化一下。

第四轮是 **Record，AI 到人**：AI 把接受的决定、文件更新和下一步整理出来，交给我们核对。记录必须反映已接受的内容，不能把建议直接当成结论。

这张图回顾的是人与 AI 的协作，不是前面 Agent Hub 内部的执行泳道。人的判断贯穿每轮，AI 帮助整理、生成和记录，后续工作再从这些共同依据继续。

## 第 22 页｜五要素沟通模板：整理流程并建立 README

对应页面：A reusable communication template: design the workflow and README

**讲图提示：**先看左边五要素，再指右边同一段完整提示词。右侧五段组成一次请求，不是五次独立对话。

最后把前面的方法整理成一个听众可以直接复用的沟通模板。左边是五项：Goal 说明要实现什么，Context 交代依据，Scope 确定交付范围，Constraints 保留边界，Acceptance 定义怎样检查结果。

右边直接用搭建 Agent Hub 举例。我们先说明希望有一个统一入口来发现和协调业务 Agent，让 AI 阅读需求和已有文件，分清已定事项与待定问题。

然后明确要求它做什么：从用户可能的问法整理 Workflow，划分主 Agent、功能 Agent 和业务 Agent 的职责，提出最小文件结构，再搭建 README，包含愿景、架构、路由、定义规范、决策和待定问题。

同时要求推荐、规划和执行分开，执行前需要确认。没有确定的工具、部署和测试，不要自行写成已经完成。

最后的交付要能检查：流程图、文件职责和 README 草稿，再用几个代表性问题走一遍，把冲突、假设和下一步列出来。

如果项目已经有了，就先读当前 README 和流程图，再说明变更，最后同步相关文件。这个模板的作用，是让一次对话既有方向，也有依据、边界和可以审核的结果。








## 第 23 页｜结尾：设计、保存约定、持续核对

对应页面：From a conversation to a shared, reviewable design

**讲图提示：**从左到右收束三个动作，不再重复所有文件和角色名称。

最后想留下三个动作。第一，先设计逻辑，把角色、判断和交接说清楚。第二，保存共同参照，把已经接受的规则写进 README、流程图和 Agent 指令。第三，每次修改以后检查受影响的文件，并把定义完成和运行验证分开。

这样我们下一次和 AI 沟通时，就不必只靠重新解释，也能明确指出当前约定和希望修改的地方。当然，仍然需要要求 AI 读取这些参照，并对结果做审核。

卡片下面的三句话，是对整场内容的简短收束：把想法保存成背景，把要求保存成规范，用文件指导 AI 实现并接受检查。
