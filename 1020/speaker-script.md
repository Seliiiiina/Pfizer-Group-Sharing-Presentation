以中文口语为主，保留 Agent、Hub、Workflow、Registry、文件名和字段名等必要英文。对应当前 21 页英文幻灯片，建议按约 25 分钟排练，实际时长以试讲为准。

## 第 1 页｜开场

对应页面：Building Agent Hub with AI

**讲图提示：**先介绍今天分享的是实现与沟通过程。

大家好，今天想结合 Agent Hub，分享我们怎么和 AI 一起，把一个想法逐渐变成有结构、能继续迭代的项目。

整场只有一个贯穿案例，就是 Agent Hub 本身。我们讲的是怎么与 AI 一起设计和实现这个项目。

我会重点讲三个问题：怎么从需求想到这些 Agent，怎么设计它们之间的 Workflow，以及怎么把讨论变成 AI 能遵循的文件和规则。这里展示的主要是项目设计和定义，真实运行效果，需要另外用调用记录和结果来验证。










## 第 2 页｜整场快照：从 Chat 到 Agent Hub

对应页面：From Chat to Agent Hub: the whole journey at a glance

**讲图提示：**沿中央箭头从左到右讲六个图标，再指出黄色、蓝色、绿色三个阶段区域。节点下方分别是这一阶段的工作和留下的产物，不需要逐项读完。

先用这张图看整场分享。最开始是 Chat，通过对话探索想法。然后把想法整理成 Structured Prompt，明确目标、背景、输入和约束。

经过讨论确认的规则，可以保存成 Reusable Instructions，比如 README 里的共同约定和各个 Agent 的指令。再用 Workflow 明确步骤、判断和交接，形成职责清楚的 Agent 设计，最后由 Agent Hub 统一入口、协调多个能力。

这不是项目真实创建顺序的还原，也不是说把 Prompt 存下来就自动变成 Agent。真正运行还需要环境、工具、状态处理和验证。当前项目能展示设计和定义如何落实，运行效果需要实际证据。

贯穿今天的设计问题是：用户知道想做什么，却不一定知道选哪个 Agent、怎样组合。接下来我们就以 Agent Hub 为例，重点看角色和流程怎样设计，以及怎样通过文件和 AI 一起把它们做具体。






## 第 3 页｜从需求拆角色

对应页面：Start with the work, then define the agent roles

**讲图提示：**先指左侧需求，再指右侧对应角色。

我们可以先不急着给 Agent 起名字，而是把用户需要的工作列出来。

用户希望有一个统一入口，理解目标、解释方案、取得确认，最后汇总结果，这些就交给 Hub。接着还会出现几个问题：找哪个能力来做，多个步骤怎么安排，谁负责执行，以及缺少能力怎么办。这些工作分别对应 Finder、Builder、Executor 和 Creator。

具体业务能力则交给业务 Agent。这一层的存在，是为了让 Hub 能组织不同类型的任务。也就是说，角色是从工作需求拆出来的。和 AI 讨论时，可以要求它说明每个角色的输入、输出、边界和交接对象，再检查有没有重复或漏掉的职责。










## 第 4 页｜职责与交接

对应页面：Agent Hub at the center, each function has a boundary

**讲图提示：**先指中间 Hub，再沿四周介绍功能角色，这表示协作关系，不表示固定执行顺序。

这张图把分工关系串起来。最上面是用户，Hub 是唯一直接与用户交互的入口。

中间的功能 Agent 各自交付不同结果：Finder 返回候选和理由，Builder 返回 Workflow Blueprint，也就是工作流蓝图，Creator 返回能力缺口与方案，Executor 返回执行状态和结果。具体业务 Agent 则由 Executor 按授权调度。

这张图表示协作关系，不是每个请求都要走完所有角色。我们真正要检查的是：每个角色完成以后，把什么交给谁。










## 第 5 页｜Workflow 主线

对应页面：Workflow: map the main path, then add decisions

**讲图提示：**先沿左侧加高的主线向下讲，再指右侧三个节点：画主线、补判断、保存规则。蓝框突出需要展开设计的区域。

有了角色，下一步就是画 Workflow。主线是：用户提需求，Hub 理解和判断，Finder 匹配能力，必要时编排，确认后执行，最后审核结果。

蓝框里是设计的重点。用户不会总按同一种方式提问，所以需要继续明确每一步的判断条件。下面只取三个关键片段，说明这些条件怎样变成规则。










## 第 6 页｜判断用户意图

对应页面：Fragment 1: identify what the user wants

**讲图提示：**对比图中左右两条路径。

第一段先判断用户想得到什么。“有哪些 Agent”和“帮我比较两份文件”，虽然都在和 Hub 对话，但期待的结果不同。

前者是了解能力，返回概览或推荐就可以，后者是执行任务，需要检查目标和材料。如果目标本身不清楚，就先问必要的问题，如果目标明确、只是文件还没给，可以先讨论能力，但执行要等待输入。

让 AI 写流程时，需要同时写清楚下一步是什么，以及应该在哪里停下来。










## 第 7 页｜选择与核验 Agent

对应页面：Fragment 2: find the right agent

**讲图提示：**先讲已指定分支，再讲未指定分支。

第二段是怎么找到合适的 Agent。用户没有指定时，交给 Finder 推荐，用户已经指定时，先检查它是否存在、适不适合这个任务，以及实际能不能运行。

指定有效，可以跳过重新推荐，指定不合适，就说明原因，再寻找替代。这里还要区分 Active 和 runtime readiness。Active 说明定义已完成、可以被发现，不能直接证明工具连接和运行已经通过验证。

一个看起来简单的用户请求，往往包含了好几个需要提前设计的判断。










## 第 8 页｜复杂请求怎样决定功能职责

对应页面：Fragment 3: break complex work into clear handoffs

**讲图提示：**重点指 Builder 和 Executor，说明设计时怎样分清规划与执行。

回到 Agent Hub 的实现：如果用户的一个请求需要多个 Agent，系统应该由谁来拆步骤、谁来执行？这正是我们需要与 AI 讨论的设计问题。

这里把规划交给 Builder，让它返回每一步的输入、输出和 dependencies，执行则交给 Executor，接收已经确认的蓝图。Hub 负责向用户解释计划并确认范围。

可以给 AI 这样的要求：不要把“规划”和“执行”写成同一个模糊职责，明确两个角色通过什么字段交接、什么时候暂停。这样 Workflow 讨论就会落实到功能指令。









## 第 9 页｜用完整 end-to-end 图把分支连起来

对应页面：The complete Agent Hub flow: keep every branch connected

**讲图提示：**左侧整图已加高，右侧四个阶段从上到下用箭头连接。按纵向顺序讲，再点击整图定位一个关键分支，不要逐节点读完。

前面看了三个片段，现在回到我们项目实际的 end-to-end 流程图。它从用户请求开始，一直覆盖到确认、执行、结果审核和重试。

右边把整图分成四段：理解与匹配，规划与确认，授权执行，最后审核与继续。缺输入回到澄清，能力不够进入缺口处理，部分失败和重试也有返回位置。

完整图的作用，是让局部修改仍然和全局逻辑连接。比如让 AI 调整一个分支时，我们要指出从哪里进入、处理完回到哪里，以及哪些确认规则不能改变，再同步检查图和指令。

这张长图在概览中不适合读细字，可以点击打开完整查看，按加减调整大小并滚动。演讲时只定位一个相关分支即可。图本身说明设计逻辑，不能作为真实执行已经通过的证据。




## 第 10 页｜用泳道看清职责和交接

对应页面：Who does what? Follow one confirmed workflow across lanes

**讲图提示：**从上到下先认识四条泳道，再沿编号从 1 讲到 9。

这页用泳道图来看一次复杂任务。每条泳道代表负责的角色，编号表示这次示例路径。

用户提出请求，Hub 理解并路由，Finder 匹配能力，用户先选择候选 Agent。用户先选择推荐的 Agent，再由 Builder 形成蓝图，Hub 向用户展示计划并确认范围。Executor 再调度业务 Agent，最后由 Hub 汇总结果。

这张图能同时回答谁负责和结果交给谁。它不表示运行耗时，也不是每个任务必须经过所有步骤。缺少输入或需要新动作时，仍要暂停并由 Hub 处理。







## 第 11 页｜直接看 README 中真实做出来的内容

对应页面：Inside our README: architecture and definition examples

**讲图提示：**先指左侧架构块，再指右侧定义模板。左边根据项目角色重新整理了缩进层级，右边是 README 模板原文快照。

前面讲了角色和流程，现在直接看我们 README 里已经保存的东西。左边把 Core Architecture 按目录关系重新分组：Agent Hub 下面是 functional-agents/，里面有 Finder、Builder、Executor 和 Creator 四个功能 Agent。Registry 和 business-subagents/ 与功能目录同级。右边是推荐的定义模板，固定为名称、Description 和 Instruction。

这些内容有两个作用：一是讨论之后留下共同参照，二是让 AI 后续生成文件时，有明确的角色和格式可以对照。它们不是运行平台截图，也不是原始聊天记录，而是直接根据真实文件原文生成的快照。

再次修改时，我们可以要求 AI 先读这些章节，再说明当前需求会影响哪些角色和文件。如果需要改变已有架构，要把变化明确提出来，不能在生成时悄悄换一套定义。





## 第 12 页｜文件结构怎么想到

对应页面：Why this structure? Give each type of information a home

**讲图提示：**每一行先讲左侧需要，再指向右侧文件。

这一页的重点不是怎么画目录树，而是为什么需要这样的结构。可以从四个协作需要推导。

第一，AI 需要跨任务使用的共同背景，所以目标、规则和决策放在 README。第二，各个角色会独立修改，所以每个 Agent 单独一个 TXT，再按功能与业务职责分组。

第三，Finder 需要简洁的能力目录，不能每次都从所有完整指令开始找，所以增加 Registry，保存发现能力需要的元数据。这里也产生了一个维护要求：索引与定义必须保持一致。

第四，待办和验证材料是不同的信息，所以分别交给 TODO 和 submission materials。

这解释的是现有结构的设计理由，不代表还原最早的创建顺序。让 AI 帮忙设计时，可以要求它提出最小结构，说明每个文件负责什么，以及哪些文件必须同步。










右侧的小柱状图补充说明为什么需要统一索引：目前有 172 份业务 Agent 定义，分为 8 类。这里不逐个介绍类别，只用真实规模说明发现与比较能力的需要。数字来自 Registry，并与定义文件核对，不表示已部署数量。


## 第 13 页｜从规范落实到 Agent 定义

对应页面：From shared standards to one agent definition

**讲图提示：**先看左侧规范来源，再指右侧生成的文件。

这里把原来的规范来源和 Agent 文件格式放在一起。左边提供参照：根 README 规定通用结构、文件格式和长度，业务目录 README 补充名称、输入和元数据规则，返回格式与用户展示规则则说明结果交给谁、怎样呈现。

右边是这些要求最终形成的文件：Name 标识能力，Description 说明什么时候选择它，Instruction 进一步写清 WHEN、DO、RETURN，也就是触发与输入、处理与边界、结果与状态。

这样和 AI 交流时，可以同时交代依据和交付物。让它按相关规范生成一份定义，再检查字符数、输入缺失时的行为，以及返回内容能否被上游使用。







## 第 14 页｜一条路由需求怎样落地与检查

对应页面：One routing requirement: define → implement → challenge

**讲图提示：**先读黄色需求，沿三步实现链路，再看下面两个挑战问题。

这一页把需求、实现和检查放在同一条链上。假设要求是：用户指定的 Agent 不适合时，说明问题并推荐替代。

先明确分支，有效时确认执行范围，无效时转 Finder。再把共同规则记录到 README 的 Subagent Selection Rules，在 Agent-Hub.txt 里实现路由与确认要求。

写完以后，下面两个问题用来挑战这条规则。指定不可用的 Agent，应该解释并推荐替代。用户说文件稍后提供，则核验能力后等待必要材料。

这里的提示词是根据现有规则整理的示例，不是原始历史对话。规则走查检查设计是否自洽，实际调用仍然需要运行证据。







## 第 15 页｜用文件依赖图看修改范围

对应页面：A file dependency map: one request can affect several files

**讲图提示：**先指上方请求，再看三类文件，最后汇入底部检查。

假设我们要求 AI 统一精简 Description，同时保留触发条件和限制。这个要求可能影响哪些文件？

左侧是 README 中的格式标准，中间是具体 Agent 定义，右侧是 Registry 中用于发现能力的描述。三个位置不能各改各的，需要在底部检查字段、引用和口径是否一致，并补充相关测试与待办。

图里的箭头表达修改依赖，不是说每次都要改全部文件。提出任务时，可以让 AI 先指出实际受影响的位置，再同步修改和检查。







## 第 16 页｜用实际修正解释三个验证关卡

对应页面：Active is a definition status, not runtime proof

**讲图提示：**先指黄色修正记录，再从左到右讲三个关卡。

这里合并了一个有记录的修正和验证方法。TODO 中记录，2026 年 10 月 15 日明确了 Active 的含义：TXT 定义完成、可以被发现，不等于已部署或运行通过。

左边第一关检查定义、角色边界，以及 TXT 和 Registry 是否一致。中间第二关要验证工具、权限和真实调用。右边第三关再看结果有没有来源支持，是否达到验收标准。

因此不能用第一关的状态代表后两关。和 AI 协作时，也要让它分别报告文件层面的完成、运行证据和结果审核，不把这些混成一句“已经完成”。







## 第 17 页｜人与 AI 的协作循环

对应页面：A visible loop: decide → develop → review → record

**讲图提示：**从上方开始，顺时针沿箭头走一圈。中间是积累下来的项目上下文，环形表示迭代过程，不表示百分比。

这张图把人与 AI 的配合放在一个循环里。人先确定目标和边界，AI 帮忙展开方案、分支和文件，人再审核是否符合业务意图、证据是否足够，把接受的内容写回项目。

新的问题出现后，就带着已有约定进入下一轮。

这里人的判断一直存在。AI 可以帮助展开和检查，但关键目标、业务含义和最终结果仍需要我们确认。

对应页面：Real feedback from this conversation changed the presentation

**讲图提示：**黄色是用户原意的英文翻译，下面是这次确实做过的修改。原始中文见下文。

## 第 19 页｜继续和 AI 工作时，怎样用流程图保持一致

对应页面：When AI revisits the project: use the diagram as a checkpoint

**讲图提示：**左侧是真实 Finder 流程图的前三个节点，右侧逐步说明怎样继续修改。

这次不是另外重画一张演讲示意图，而是把我们项目里已经存在的 Finder 流程图取一段放出来。它先接收目标和约束，再识别分类与标签，然后从 Registry 检索候选。完整流程里还包含适配评估、排序和交接。

它的作用是让规则有可对照的位置。下次让 AI 修改时，先要求它读取 README、相关流程图和指令，再指出受影响的节点或分支。确定变化后，同步修改规则、图和相关文件，最后拿问题沿着分支走一遍。

比如可以说：保留识别标签、检索候选、评估适配的顺序，如果建议改变，先解释原因。这样更容易发现 AI 在重复生成或多轮修改时出现的遗漏、冲突和职责漂移。

不过有文件不等于 AI 一定会自动读，也不能保证逻辑永远正确。仍要明确引用当前版本并检查结果。若图和指令不一致，应先提出冲突并确认修正。





## 第 20 页｜五要素沟通模板：整理流程并建立 README

对应页面：A reusable communication template: design the workflow and README

**讲图提示：**先看左边五要素，再指右边同一段完整提示词。右侧五段组成一次请求，不是五次独立对话。

最后把前面的方法整理成一个听众可以直接复用的沟通模板。左边是五项：Goal 说明要实现什么，Context 交代依据，Scope 确定交付范围，Constraints 保留边界，Acceptance 定义怎样检查结果。

右边直接用搭建 Agent Hub 举例。我们先说明希望有一个统一入口来发现和协调业务 Agent，让 AI 阅读需求和已有文件，分清已定事项与待定问题。

然后明确要求它做什么：从用户可能的问法整理 Workflow，划分主 Agent、功能 Agent 和业务 Agent 的职责，提出最小文件结构，再搭建 README，包含愿景、架构、路由、定义规范、决策和待定问题。

同时要求推荐、规划和执行分开，执行前需要确认。没有确定的工具、部署和测试，不要自行写成已经完成。

最后的交付要能检查：流程图、文件职责和 README 草稿，再用几个代表性问题走一遍，把冲突、假设和下一步列出来。

如果项目已经有了，就先读当前 README 和流程图，再说明变更，最后同步相关文件。这个模板的作用，是让一次对话既有方向，也有依据、边界和可以审核的结果。


## 第 21 页｜结尾：设计、保存约定、持续核对

对应页面：From a conversation to a shared, reviewable design
